In Wirespec, everything that gets sent over the wire is a type.

## Primitive

This section describes the primitive types used in Wirespec:

- `String`
- `Boolean`
- `Integer`
- `Integer32`
- `Number` (For Real numbers, so i.e. float/double)
- `Number32`
- `Bytes`
- `Unit` (Only used to indicate the absence of a response body)

## Composite

A composite type in wirespec allows you to group together fields of different types under a single named structure.
Think of it as creating your own custom data structure or record. It's the foundation for building complex data
representations and is what you would typically use to define your Data Transfer Objects (DTOs) or similar data
structures.

```wirespec
type User {
    id: Integer,
    name: String,
}
```

### Annotations on Types

Types can be annotated to provide metadata for code generation or validation:

```wirespec
@Name("users")
type User {
    id: Integer,
    name: String,
}
```

It is also possible to reference other types that you defined:

```wirespec
type Person {
    name: String,
    address: Address
}

type Address {
    streetName: String,
    houseNumber: Integer
}
```

The same applies to other types, such as [refined](#refined):

```wirespec
type Person {
  firstname: Name,
  lastName: Name
}

type Name = String(/^[0-9a-zA-Z]{1,50}$/g)
```

You can use backticks to create field names that would otherwise not be valid with the compiler, such as names that
start with uppercase letters:

```wirespec
type User {
    `UserID`: Integer,
    `User-Type`: String
}
```

### Annotations on Fields

Fields within composite types can also be annotated to provide metadata for individual fields:

```wirespec
type User {
    @Deprecated
    name: String,
    age: Integer
}
```

### Field type modifiers

Fields of composite types can be defined as optional using a `?`:

```wirespec
type Product {
    description: String?,
}
```

Or, as a list using `[]`:

```wirespec
type Product {
    tags: String[]
}
```

Lastly, you can create a dictionary by placing brackets around the type. The resulting map/dict will map from `String`
to the specified type, `String -> String` in this example:

```wirespec
type Person {
    details: { String }
}
```

### Default values

A field can declare a default value with `=`. The default is used when a value for the field is not provided, for
example when a client leaves the field out of a request body:

```wirespec
type Settings {
    name: String = "anonymous",
    retries: Integer = 3,
    port: Integer32(0, 65535) = 8080,
    ratio: Number = 1.5,
    active: Boolean = true,
    nickname: String? = null
}
```

#### Supported values

Defaults can be set on fields of a primitive type, and nullable fields can also default to `null`:

| Field type                 | Default value                                | Example                          |
|----------------------------|----------------------------------------------|----------------------------------|
| `String`                   | A string literal                             | `name: String = "anonymous"`     |
| `Integer`, `Integer32`     | An integer literal, which may be negative    | `offset: Integer = -1`           |
| `Number`, `Number32`       | A number or an integer literal               | `ratio: Number = 1.5`            |
| `Boolean`                  | `true` or `false`                            | `active: Boolean = true`         |
| Any nullable field above   | `null` or a value of the field's type        | `limit: Integer? = 10`           |

String literals support the escapes `\"`, `\\`, `\n`, `\r` and `\t`. An integer literal on a `Number` field is read as a
number, so `scale: Number = 2` is the same as `scale: Number = 2.0`.

Defaults are not supported on lists, dictionaries, enums, refined types or references to other types.

#### Validation

The compiler checks every default against its field. Each of these fields is a compile error:

- `name: String = 1`: the value does not match the field's type.
- `count: Integer = 1.5`: an `Integer` needs a whole number.
- `small: Integer32 = 2147483648`: the value does not fit in 32 bits.
- `score: Integer(0, 10) = 11`: the value is outside the field's bounds.
- `nickname: String = null`: only nullable fields can default to `null`.

The error points at the value, for example: `Invalid default value 11 for field score of type Integer`. A regular
expression constraint on a `String` field is not checked against its default.

Defaults are only allowed on the fields of a `type`. Endpoint queries and headers, and rpc parameters, cannot have
defaults:

```wirespec
// Error: Default values are only allowed on fields of a type definition, not on: limit
endpoint GetTodos GET /todos ? {limit: Integer = 10} -> {
    200 -> Todo[]
}
```

#### Generated code

| Emitter                                   | Defaults                                                                 |
|-------------------------------------------|--------------------------------------------------------------------------|
| Kotlin                                    | Generated as constructor parameter defaults, see the [Kotlin emitter](../emitters/emitters-kotlin.mdx#default-values) |
| Java, TypeScript, Python, Rust and Scala  | Not generated yet, the fields are emitted without a default              |
| Wirespec, OpenAPI and Avro                | Not written to the output yet                                            |

#### Ignoring defaults

To leave all defaults out of the generated code, turn on the ignore defaults option of the plugin. Defaults are still
checked, so an invalid default stays a compile error.

CLI:

```shell
wirespec compile -i ./wirespec -l Kotlin --ignore-defaults
```

Gradle:

```kotlin
tasks.register<CompileWirespecTask>("wirespec-kotlin") {
    input = layout.projectDirectory.dir("src/main/wirespec")
    output = layout.buildDirectory.dir("generated")
    languages.set(listOf(Language.Kotlin))
    ignoreDefaults.set(true)
}
```

Maven:

```xml
<configuration>
    <input>${project.basedir}/src/main/wirespec</input>
    <output>${project.build.directory}/generated-sources/wirespec</output>
    <languages>
        <language>Kotlin</language>
    </languages>
    <ignoreDefaults>true</ignoreDefaults>
</configuration>
```

## Enum

Enums (enumerations) in Wirespec are used to define a type that can only take on one of a predefined set of named
values. Enums are ideal for situations where a field can only have a fixed number of possibilities:

```wirespec
enum Direction {
    NORTH, SOUTH, WEST, EAST
}
```

Both upper case and camel case values are accepted:

```wirespec
enum Role {
    SoftwareEngineer,
    SystemAdmin
}
```

Enums can also be annotated:

```wirespec
@StringEnum
@JsonProperty("role_type")
enum Role {
    SoftwareEngineer,
    SystemAdmin
}
```

## Refined

Using simple string values as types is often too lenient. You might need to enforce specific patterns, ranges, or
formats for your data. Refined types allow you to be more specific, constrained types based on existing ones, ensuring
data conforms to certain rules. A common use case for refined types is to use a regular expression to define allowed
patterns for strings. You can define a refined type as follows:

```wirespec
type Date = String(/^([0-9]{2}-[0-9]{2}-20[0-9]{2})$/g)
```

```wirespec
type Age = Integer(0, _)
```

```wirespec
type Score = Number(0.0, 10.0)
```

## Union

In Wirespec, a union type represents a value that can be one of several different types. The key characteristic is that
at any given time, the value holds only one of those types. It can be defined using `type` keyword and consists of a
list of non-primitive types separated by a `|` (union operator):

```wirespec
type Result = Win | Loss

type Win {
    points: Integer,
    nextOpponent: String
}

type Loss {
   points: Integer
}
```
