## Definitions

Definitions are the core building blocks of Wirespec. This is a collection of basic syntax elements and examples
necessary for creating these definitions:

- [Endpoint](language/endpoints)
- [Channel](language/channels)
- [RPC](language/rpc)
- [Type](language/types)
- [Part](language/parts)

A Wirespec file consists of a set of definitions in any order.

## Comments

Just like most modern languages, Wirespec supports single-line (or **end-of-line**) and multi-line (**block**) comments. Comments can only be placed above definitions and are used to document them:

```wirespec
// This is an end-of-line comment
endpoint GetTodos GET /todos -> {
    200 -> Todo[]
}

/* This is a block comment
 * on multiple lines
 */
type Todo {
    id: Integer,
    title: String,
    completed: Boolean
}
```

Comments placed above definitions are also used to emit comments in the target languages when code is generated, though
this behavior may vary depending on the target language and emitter implementation.

## Annotations

Annotations provide a way to attach metadata to definitions in Wirespec. They are denoted by the `@` symbol followed by
an identifier and can optionally include parameters. Annotations can be applied to endpoints, channels, rpcs, types, and
enums to provide additional information for code generation or processing. Note that you need to write an
[IR extension](../plugins/plugins.md#ir-extensions) to make use of these annotations:

```wirespec
@Deprecated("No longer used in V2")
type User {
    id: Integer,
    name: String
}

@Deprecated("Use GetUserV2 instead")
endpoint GetUser GET /users/{id: Integer} -> {
    200 -> User
}
```

Annotations can also have named attributes with different value types:

```wirespec
@Security(role: "admin", level: 1)
@RateLimit(requests: 100, period: "hour")
endpoint AdminEndpoint GET /admin -> {
    200 -> AdminData
}

@Validate(min: 1, max: 100, required: true)
type Score {
    value: Integer
}
```

A value can also be an array of strings, such as `["todos", "audit"]` or the empty `[]`, or a dictionary. A name
that is not an identifier, such as `$ref` or `x-trace.id`, is written between quotes:

```wirespec
@Kafka(topics: ["todos", "audit"], headers: { "x-trace.id": "uuid", retries: "3" })
type Todo {
    id: String
}
```

Multiple annotations can be applied to the same definition:

```wirespec
@JsonSerializable("strict")
@ValidateInput
type CreateUserRequest {
    name: String,
    email: String
}
```

### The file header

An annotation written as `@spec:Name` applies to the whole specification: every file compiled together. An annotation
written as `@file:Name` applies to the file it is written in. They take parameters like any other annotation, and
together they form the file header:

```wirespec
@spec:OpenAPIServer("https://api.example.com/v2", description: "Production")
@spec:OpenAPISecurityScheme("bearerAuth", type: "http", scheme: "bearer", bearerFormat: "JWT")
@file:Owner("customers")

type Customer {
    id: String
}
```

- The header is the first thing in a file. Only empty lines may come before it, not even a comment.
- `@spec:` and `@file:` annotations may be mixed in any order.
- An empty line separates the header from whatever follows it.
- A `@spec:` or `@file:` annotation anywhere else is an error.
- A file may hold nothing but a header with `@spec:` annotations, so the annotations of the whole specification can
  have a file of their own. Such a file cannot hold `@file:` annotations: they describe the definitions in the file.
- Spec annotations are unique: the same `@spec:` annotation twice, in one file or in two, is an error.

The files of a directory are read in the order of their paths, so the spec annotations of several files come in the
same order on every machine. An emitter that reads spec annotations decides what else counts as the same: the
[OpenAPI emitters](../converters/openapi.md#several-files), for example, collect the servers and tags of all files but
accept each server URL and tag name once, and the default security from one file only.

An emitter or [IR extension](../plugins/plugins.md#ir-extensions) finds the spec annotations on the root of the AST,
each with the file it is written in, and the file annotations on each module.

## Default values

Fields of a [type](language/types#default-values) can declare a default value with `=`. Defaults are supported on
primitive and enum fields, and any nullable field can default to `null`:

```wirespec
type Settings {
    name: String = "anonymous",
    retries: Integer = 3,
    active: Boolean = true,
    status: Status = ACTIVE,
    nickname: String? = null
}

enum Status {
    ACTIVE, INACTIVE
}
```

Not every language can generate defaults yet. See [Default values](language/types#default-values) for the rules, the
languages that support them and how to leave them out.

## Coding Conventions

Commonly known and easy-to-follow coding conventions are vital for any language. Here we provide guidelines on the code
style and code organization for projects that use Wirespec.

### Source file names

A wirespec file can have any name as long as it a `.ws` extension. However, it is a good idea to name a Wirespec
file after the resource it describes, in [kebab case](https://en.wikipedia.org/wiki/Letter_case#Kebab_case). Generated
output gets written to a file in the target language with a matching name (if allowed).

### Identifiers

All definitions in Wirespec have an identifier that is used to either reference types in other places, or in case of
channels and endpoints, for code generation. Identifiers should be named in
[upper camel case](https://en.wikipedia.org/wiki/Camel_case).

### Indentation

Use four spaces for indentation. Do not use tabs.

For curly braces, put the opening brace at the end of the line where the construct begins, and the closing brace on a
separate line aligned horizontally with the opening construct.

```wirespec
endpoint GetTodos GET /todos -> {
    200 -> Todo[]
}
```
