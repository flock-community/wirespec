The Kotest integration turns your Wirespec contract into a typed test DSL for [Kotest](https://kotest.io). An
[IR extension](../plugins/plugins.md#ir-extensions) generates a `generate` entry point next to every model, endpoint,
channel and rpc. Each one returns a Kotest [`Gen`](https://kotest.io/docs/proptest/property-test-generators.html) of
values that satisfy the contract, and you only spell out the fields a test cares about:

```kotlin
val response = CreateTodo.generate.request {
    body { name("Buy milk") }
}.call()

response.shouldBeInstanceOf<CreateTodo.Response201>()
```

The fields you don't pin are drawn from the contract: string patterns, integer and number bounds, nullability, enums,
refined types, lists and nested records are all respected. `call()` sends the request over your own transport and
checks the response against the contract, so a test fails when the service answers with an undeclared status or a body
that doesn't match.

The integration has two parts that you can use together or on their own:

1. The **scenario DSL**, generated by the `KotestDsl` extension, which builds and sends requests, messages and rpc
   calls.
2. A **`Wirespec.Generator`** backed by Kotest `Arb`s, which drives the generated `*Generator` factories directly.

## Setup

Add the integration and `kotest-property` to the source set that compiles the generated code. The Wirespec runtime
comes from `wirespec-jvm`:

<Tabs>
  <TabItem value="gradle" label="Gradle">
    ```gradle title="build.gradle.kts"
    dependencies {
        implementation("community.flock.wirespec.integration:wirespec-jvm:{{WIRESPEC_VERSION}}")
        implementation("community.flock.wirespec.integration:kotest-jvm:{{WIRESPEC_VERSION}}")
        implementation("io.kotest:kotest-property:<kotest-version>")
        testImplementation("io.kotest:kotest-runner-junit5:<kotest-version>")
    }
    ```
  </TabItem>
  <TabItem value="maven" label="Maven">
    ```xml title="pom.xml"
    <dependency>
        <groupId>community.flock.wirespec.integration</groupId>
        <artifactId>wirespec-jvm</artifactId>
        <version>{{WIRESPEC_VERSION}}</version>
    </dependency>
    <dependency>
        <groupId>community.flock.wirespec.integration</groupId>
        <artifactId>kotest-jvm</artifactId>
        <version>{{WIRESPEC_VERSION}}</version>
    </dependency>
    <dependency>
        <groupId>io.kotest</groupId>
        <artifactId>kotest-property-jvm</artifactId>

        <groupId>io.kotest</groupId>
    ```

The extension applies to the **Kotlin** target only and is bundled with every Wirespec plugin as `KotestDsl`.
Register it with `extensionClasses`: by name in Maven, by class in Gradle. Disable shared-code emission
(`shared = false`) so the Wirespec runtime classes come from `wirespec-jvm`, which is what the integration is compiled
against.

<Tabs>
  <TabItem value="gradle" label="Gradle">
    ```gradle title="build.gradle.kts"
    import community.flock.wirespec.integration.kotest.extension.KotestDslExtension
    import community.flock.wirespec.plugin.gradle.CompileWirespecTask
    import community.flock.wirespec.plugin.Language

    tasks.register<CompileWirespecTask>("wirespec-compile") {
        input = layout.projectDirectory.dir("src/main/wirespec")
        output = layout.buildDirectory.dir("generated")
        packageName = "community.flock.wirespec.generated"
        languages = listOf(Language.Kotlin)
        shared = false
        extensionClasses = listOf(KotestDslExtension::class.java)
    }
    ```
  </TabItem>
  <TabItem value="maven" label="Maven">
    ```xml title="pom.xml"
    <plugin>
        <groupId>community.flock.wirespec.plugin.maven</groupId>
        <artifactId>wirespec-maven-plugin</artifactId>
        <version>{{WIRESPEC_VERSION}}</version>
        <executions>
            <execution>
                <id>kotlin</id>
                <goals>
                    <goal>compile</goal>
                </goals>
                <configuration>
                    <input>${project.basedir}/src/main/wirespec</input>

                    <languages>
                        <language>Kotlin</language>

                    <shared>false</shared>

    </plugin>
    ```

compile the generated code with `-java-parameters`. Spring Boot's Gradle plugin already sets it for you:

    ```gradle title="build.gradle.kts"
            javaParameters = true
    ```

    ```xml title="pom.xml"
    </plugin>
    ```

:::warning
The DSL is generated into `<packageName>.kotest`, in the same output as the models, so it is compiled wherever the
models are. When the models are part of your main source set, the integration and `kotest-property` have to be main
dependencies too, as above. The generated models themselves stay dependency-free: the extension only adds an empty
`companion object` to each record with fields, so `<Type>.generate` has a receiver.
:::

## Quick start

Given this contract:

```wirespec title="src/main/wirespec/todo.ws"
type Todo {
    id: String,
    name: String,
    done: Boolean
}

type Error {
    code: Integer,
    description: String
}

endpoint GetTodos GET /api/todos ? {done: Boolean?} -> {
    200 -> Todo[]
}

endpoint CreateTodo POST Todo /api/todos -> {
    201 -> Todo
}

endpoint GetTodoById GET /api/todos/{id: String} -> {
    200 -> Todo
    404 -> Error
}
```

a spec against a running service looks like this:

```kotlin
import community.flock.wirespec.generated.endpoint.CreateTodo
import community.flock.wirespec.generated.endpoint.GetTodoById
import community.flock.wirespec.generated.kotest.call
import community.flock.wirespec.generated.kotest.generate
import community.flock.wirespec.integration.jvm.transport.HttpTransportation
import community.flock.wirespec.integration.kotest.extension.WirespecEndpointExtension

class TodoSpec : FunSpec({
    extension(WirespecEndpointExtension(HttpTransportation("http://localhost:8080"), serialization))

    test("a created todo can be fetched") {
        val created = CreateTodo.generate.request {
            body { name("Buy milk") }
        }.call()
        created.shouldBeInstanceOf<CreateTodo.Response201>()

        val fetched = GetTodoById.generate.request {
            path { id(created.body.id) }
        }.call()
        fetched.shouldBeInstanceOf<GetTodoById.Response200>()
        fetched.body.name shouldBe "Buy milk"
    }
})
```

`serialization` is any `Wirespec.Serialization`, for example the one from the [Jackson](./integration-jackson.mdx)
integration. `HttpTransportation` is a `Wirespec.Transportation` on the JDK `HttpClient`, shipped by the `jvm`
integration (`community.flock.wirespec.integration:jvm-jvm`); pass your own transportation to test through any other
client.

## The scenario DSL

Every generated declaration lives in `<packageName>.kotest`. Import `generate`, plus the terminals you use (`call`,
`send`, `mock`), from that package.

### Pinning fields

Every builder exposes each field twice: as a `Gen` property, and as a function of the same name that pins a constant.
A nested record field also gets a `<field>Block` that opens the nested record's builder, so you can pin fields at any
depth:

```kotlin
CreateTodo.generate.request {
    body {
        name("Buy milk")                   // the same as: name = Arb.constant("Buy milk")
        done = Arb.boolean()               // any Gen or Arb works
    }
}
```

Every field you don't pin keeps the value the generator drew for it. In a record builder, a refined field is pinned by
its inner value and the integration wraps it for you: `id("u-042")` for a `UserId`. Endpoint path, query and header
parameters take the refined type itself.

A record has a single `<Type>Builder` class, which every builder of that record shares: a request body, a channel
message, an rpc outcome and the standalone `<Type>.generate`.

### Models

Every record type gets a `generate` function on its companion object:

```kotlin
val todos: Gen<Todo> = Todo.generate { done(false) }

checkAll(todos) { todo -> todo.done shouldBe false }
val one: Todo = todos.draw()
```

`draw()` (from `community.flock.wirespec.integration.kotest.dsl`) takes one value from any `Gen`. It accepts a
`RandomSource`, so you can draw the same value again from the same seed.

### Endpoints

`<Endpoint>.generate.request { … }` returns a `Gen` of requests. The block configures the `path`, `query`, `header`
and `body` slots that the endpoint declares:

```kotlin
val byId: Gen<GetTodoById.Request> = GetTodoById.generate.request { path { id("42") } }
val open: Gen<GetTodos.Request> = GetTodos.generate.request { query { done(false) } }
val created: Gen<CreateTodo.Request> = CreateTodo.generate.request { body { name("Buy milk") } }
```

- **Path, query and header parameters are not generated.** Set every required one, or building the request fails
  with a message naming the missing parameter. A nullable parameter you leave out is sent as `null`.
- **The body is generated**, and its block only pins fields. For a list body the block applies to every element, and
  `bodyCount` (default `1..3`) sets how many elements are drawn. A primitive body is pinned with `body(value)`.

`call()` draws one request, sends it through the transportation of the [ambient context](#wiring-the-transport) and
returns the typed response. The response is checked against the contract first: an undeclared status, or a body that
doesn't deserialize into the matching response, fails the test with an `AssertionError` that names the endpoint and
prints the seed.

```kotlin
val response = GetTodoById.generate.request { path { id("42") } }.call()
response.shouldBeInstanceOf<GetTodoById.Response200>()
```

Each declared status also gets a response entry point, `response<status> { … }`, with a slot for the body and each
declared header:

```kotlin
val notFound: GetTodoById.Response404 = GetTodoById.generate.response404 {
    body = Error.generate { code(404L) }
}.draw()
```

A response `Gen` can stub a downstream service. `mock { request -> … }` draws one response and registers it on the
mock server of the ambient context, for every request to that endpoint the typed predicate accepts:

```kotlin
GetTodoById.generate.response200 {
    body = Todo.generate { name("Buy milk") }
}.mock { request -> request.path.id == "42" }
```

### Channels

`<Channel>.generate.message { … }` returns a `Gen` of messages, and `send()` publishes one through the channel
transport of the ambient context. It returns the message it sent, so you can assert on what a consumer did with it:

```kotlin
val sent = CampaignEvents.generate
    .message { eventType(CampaignEventType.ENDED) }
    .send("campaign-events")
```

`send()` takes an optional topic and key. Without a topic it publishes to the simple name of the channel, here
`CampaignEvents`. A channel with a primitive payload has `message()` without a block. The DSL only drives the sending
side: assert on what your application published with your own consumer.

### Rpcs

Wirespec defines no transport for an rpc, so `call()` runs on the `Service` implementation you register. Given:

```wirespec
type User {
    id: UserId,
    name: String
}

type NotFound {
    reason: String
}

type UserId = String(/^u-[0-9]{3}$/g)

rpc GetUser {
    id: UserId
} -> User ! NotFound
```

`<Rpc>.generate.request { … }` returns a `Gen` of `<Rpc>Request`, a data class holding the rpc's parameters, and
`call()` hands one to the registered `<Rpc>.Service`:

```kotlin
val response: GetUser.Response = GetUser.generate.request { id("u-042") }.call()
response.shouldBeInstanceOf<GetUser.Result>()
```

`call()` returns the rpc's `Response` when it declares an error, and the result type otherwise. The outcomes are
`Gen`s too: `result { … }`, and `error { … }` when the rpc declares an error. They take the record's builder when the
outcome is a record, or a list of records, in which case a pinned field applies to every element. They are handy to
stub a service that the code under test depends on:

```kotlin
val userService = GetUser.Service { GetUser.generate.result { name("Alice") }.draw() }
val missing: GetUser.Error = GetUser.generate.error { reason("gone") }.draw()
```

The parameters follow the same rules as model fields, so `GetUser.generate.request()` without a block draws an `id`
that matches its pattern.

## Wiring the transport

The DSL takes its transport, and a `RandomSource` per test, from an ambient context. A Kotest extension installs one
for each kind of operation; register the ones your spec uses:

| Extension                   | Backs                   | Takes                                                      |
|-----------------------------|-------------------------|------------------------------------------------------------|
| `WirespecEndpointExtension` | `call()` on an endpoint | a `Wirespec.Transportation` and a `Wirespec.Serialization` |
| `WirespecMockExtension`     | `mock { … }`            | a `MockServer` and a `Wirespec.Serialization`              |
| `WirespecChannelExtension`  | `send()`                | a `ChannelTransport` and a `Wirespec.Serialization`        |
| `WirespecRpcExtension`      | `call()` on an rpc      | the `Service` implementations                              |

They live in `community.flock.wirespec.integration.kotest.extension` and compose: register several and they share one
`RandomSource` per test.

```kotlin
class TodoSpec : FunSpec({
    extension(WirespecEndpointExtension(transportation, serialization))
    extension(WirespecMockExtension(mockServer, serialization))
    extension(WirespecChannelExtension(channelTransport, serialization))
    extension(WirespecRpcExtension(userService))
})
```

An operation whose extension is missing fails with a message naming the extension to add. An rpc `call()` also fails
when no registered service, or more than one, implements that rpc's `Service`.

`ChannelTransport` and `MockServer` are small interfaces you implement for your broker and mock server:
`ChannelTransport.publish(topic, key, body)` sends a serialized message, and `MockServer` has `stub(stub)` and
`reset()`. The [example](#a-full-example) implements them for Kafka and WireMock.

When the transport is only known once the test runs, for example a Spring Boot server on a random port, use the
factory forms. They take `suspend` lambdas and call them for every test, or for every spec for a channel transport or a
mock server they own:

```kotlin
// serialization(), port(), bootstrapServers() and KafkaChannelTransport are your own helpers.
class ProjectConfig : AbstractProjectConfig() {
    override val extensions: List<Extension> = listOf(
        SpringExtension(),
        WirespecEndpointExtension(
            serialization = { serialization() },
            transportation = { HttpTransportation("http://localhost:${port()}") },
        ),
        WirespecChannelExtension(
            serialization = { serialization() },
            transportation = { KafkaChannelTransport(bootstrapServers()) },
        ),
    )
}
```

The channel factory takes an optional `reset` that runs before each test, and closes an `AutoCloseable` transport after
its spec. `WirespecMockExtension(serialization = { … }, server = { … })` does the same for a server it starts, while
`WirespecMockExtension(server, serialization = { … })` resets a server you own before each test and leaves it running.

## Generating models directly

The DSL builds on a `Wirespec.Generator` backed by Kotest `Arb`s. You can also use it on its own, with the
`*Generator` factories the Kotlin emitter generates for every model:

```kotlin
import community.flock.wirespec.integration.kotest.generator.kotestWirespecKotlinGenerator

val generator = kotestWirespecKotlinGenerator(seed = 1L)
val todo: Todo = TodoGenerator.generate(generator, emptyList())
```

The same seed gives the same values for the same type. A nullable field is `null` for about one in five paths, so tests
exercise the null branches too. The generator keeps state while it generates and is not thread-safe: create one per
test instead of sharing it between tests that run concurrently.

### Overrides

Pin or customise generated values in the builder block. Given

```wirespec
type TodoList {
    owner: String,
    todos: Todo[]
}
```

you can override fields by their path, or by the record they belong to:

```kotlin
val generator = kotestWirespecKotlinGenerator(seed = 1L) {
    // By path, in exact segments. `*` matches any single segment, such as a list index.
    registerPath("owner", value = "alice")
    registerPath("todos", "*", "name") { Arb.string(5..10) }
    registerPath("todos", "0", "id", value = "FIXED-ID")

    // By record and field, checked by the compiler. The same by name:
    // registerFieldByTypeName("community.flock.wirespec.generated.model.Todo", "done", value = false)
    registerField(Todo::done, value = false)
}

val list: TodoList = TodoListGenerator.generate(generator, emptyList())
```

- When several path patterns match a field, the most specific one wins, and a path override wins over a field
  override. A `@Seed` field wins over both.
- A field override only applies to a record that is generated inside another record, like each `Todo` above. For the
  record you generate at the root, override its fields by path.
- A factory returns any Kotest `Gen`, an `Arb` or an `Exhaustive`.
- Pass `value =` by name: `registerPath("todos", "id", "FIXED")` registers the path `todos/id/FIXED`, because the
  path is a vararg.
- Registering the same path or field twice fails straight away. Two equally specific paths that match the same field
  fail when that field is generated.
- An override on a refined field takes the inner value, which the generator wraps. A value of the wrong type fails
  with a message naming the path, the expected type and the type it got.

### `@Seed`

A field annotated with `@Seed` takes its value from the path its record is generated at, so a record can be
regenerated from its id alone:

```wirespec
type Project {
    @Seed id: String,
    name: String
}
```

```kotlin
val project = ProjectGenerator.generate(generator, listOf("proj-42"))
project.id shouldBe "proj-42"
```

For a list of records, the generator draws each element's seed first and then generates the element from it, so
every element gets a stable identity.
