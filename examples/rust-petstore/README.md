# Wirespec Rust example: Petstore

A small Rust client and server for the [Petstore](petstore.json). The models, endpoints and client are generated by
the Wirespec CLI built from this repository.

The generated code only uses the standard library and `regex`. It doesn't know how to write JSON or how to talk HTTP.
You connect it by implementing two traits:

- **`Serialization`** turns bodies, path parameters, query parameters and headers into bytes and strings, and back.
  This example uses `serde_json`.
- **`Transportation`** sends a raw request and returns the raw response. This example uses `reqwest`. On the server,
  `actix-web` is the transport.

The rest of this README shows how these pieces fit together.

## Run it

From the repository root, this generates the code, then builds and tests the example. It installs cargo when it is
missing:

```bash
./gradlew :examples:build-rust-petstore
```

From this directory, you need Rust 1.85 or newer:

```bash
bash gen.sh
```

```bash
cargo test
```

```bash
cargo run --bin server
```

```bash
cargo run --bin client
```

The client calls `http://localhost:8080` by default. To call another Petstore, pass its base URL:
`cargo run --bin client -- <base url>`.

## Generate the code

`gen.sh` builds the native Wirespec CLI for your platform from this repository, if it isn't built yet, and runs:

```bash
wirespec convert OpenAPIV2 -i petstore.json -o src/generated -l Rust -p '' --shared
```

`--shared` also writes `wirespec.rs`, which holds the traits shared by all endpoints. `-p ''` keeps the output flat.

`src/generated` is not committed. Run `gen.sh` again after changing the Rust emitter.

## Project layout

```text

src/generated/          generated by Wirespec
  wirespec.rs           shared traits: Serialization, Transportation, RawRequest, RawResponse, ...
  model/                Pet, Order, User, ... and the enums PetStatus and OrderStatus
  endpoint/             one module per endpoint
  client.rs, client/    Client, which can call every endpoint
src/serialization.rs    Serialization: JSON with serde_json
src/transportation.rs   Transportation: HTTP with reqwest

src/bin/client.rs       calls the Petstore

```

## How the integration works

Each endpoint gets its own module. Take `endpoint/get_pet_by_id.rs` as an example:

- `Request` holds the typed path, queries, headers and body.
- `Response` is an enum with one variant per status code: `Response200(Response200)`, `Response400(..)` and
  `Response404(..)`.
- `GetPetById::Handler` is the trait the server implements: `async fn get_pet_by_id(&self, request: Request) -> Response`.
- `GetPetById::Call` is the trait the client offers: `async fn get_pet_by_id(&self, pet_id: i64) -> Response`.
- `GetPetById::to_raw_request`, `from_raw_request`, `to_raw_response` and `from_raw_response` convert between the typed
  request or response and a `RawRequest` or `RawResponse`. Each one takes a `Serializer` or `Deserializer`.
- `GetPetById::Api` gives the path template, `/pet/{petId}`, and the method, `GET`.

`RawRequest` and `RawResponse` are plain data: the method or status code, the path segments, the query parameters and
headers as `HashMap<String, Vec<String>>`, and the body as `Option<Vec<u8>>`. A call goes through these steps:

```text
client                                                 server
petstore.get_pet_by_id(1)                              PetStore::get_pet_by_id(request)
  │ to_raw_request(&Json, ..)                            ▲ from_raw_request(&Json, ..)
  ▼                                                      │
RawRequest ──► Http (reqwest) ──── HTTP ────► actix-web ──► RawRequest
RawResponse ◄─ Http (reqwest) ◄─── HTTP ───── actix-web ◄── RawResponse
  │ from_raw_response(&Json, ..)                         ▲ to_raw_response(&Json, ..)
  ▼                                                      │
get_pet_by_id::Response                                get_pet_by_id::Response
```

### Serialization: `src/serialization.rs`

`Serialization` combines three pairs of traits. `Json` implements all of them:

| Traits                                    | Used for                       | Implementation                         |
|-------------------------------------------|--------------------------------|----------------------------------------|
| `BodySerializer`, `BodyDeserializer`      | request and response bodies    | JSON, with `serde_json`                |
| `PathSerializer`, `PathDeserializer`      | path parameters                | `Display` and `FromStr`                |
| `ParamSerializer`, `ParamDeserializer`    | query parameters and headers   | one string per value, `Vec<String>`    |

The generated code calls, for example, `serialization.serialize_body(&pet, TypeId::of::<Pet>())`. The body arrives as
a plain `T: 'static` with no serde bound, because the generated models don't derive `Serialize`. So `Json` first has
to work out which concrete type it got:

- `petstore_types!` lists every type the Petstore sends or receives as a body or parameter. It generates `to_json` and
  `from_json`, which downcast the value to the right type with `std::any::Any`.
- Every type in that list implements a small `JsonValue` trait:
  - `object!` handles structs. Wirespec renames fields to snake case (`photoUrls` becomes `photo_urls`), so the macro
    maps each field back to its name in the contract:
    `object!(Pet { id: "id", photo_urls: "photoUrls", ... })`.
  - `enumeration!` handles enums. It uses `label` and `from_label` from the generated `Enum` trait, so
    `PetStatus::Available` is written as `"available"`.
  - Generic impls cover `String`, the integer types, `bool`, `Option`, `Vec` and `HashMap`.

When the contract changes, update `petstore_types!` and the `object!` mappings. If a type is missing,
`Json` panics with `... is not a Petstore type`.

Query parameters and headers arrive as strings and carry no type information. `deserialize_param` therefore tries
each value as a list, then as a string, then as a literal such as `42`.

### Transportation: `src/transportation.rs`

`Transportation` has a single method, `async fn transport(&self, request: &RawRequest) -> RawResponse`. `Http`
implements it with `reqwest`:

1. It appends the path segments to the base URL, which percent-encodes them.
2. It adds the query parameters and headers.
3. It sends the body as `application/json`.
4. It copies the status, headers and body into a `RawResponse`.

You don't write a client yourself. The generated `Client` in `client.rs` implements the `Call` trait of every endpoint.
You give it a `Serialization` and a `Transportation`:

```rust
use get_pet_by_id::GetPetById::Call as _;

let petstore = Client { serialization: Json, transportation: Http::new("http://localhost:8080") };

match petstore.get_pet_by_id(1).await {
    get_pet_by_id::Response::Response200(response) => println!("{:?}", response.body),
    get_pet_by_id::Response::Response400(_) => println!("Invalid id"),
    get_pet_by_id::Response::Response404(_) => println!("Not found"),
}
```

Because `Response` is an enum of the status codes in the contract, the `match` has to handle every status the contract
defines.

### Server: `src/server.rs`

On the server, actix-web plays the role of the transport. `PetStore` implements the `Handler` trait of each endpoint
it serves:

```rust
impl get_pet_by_id::GetPetById::Handler for PetStore {
    async fn get_pet_by_id(&self, request: get_pet_by_id::Request) -> get_pet_by_id::Response {
        match pets().into_iter().find(|pet| pet.id == Some(request.path.pet_id)) {
            Some(pet) => get_pet_by_id::Response200::new(pet).into(),
            None => get_pet_by_id::Response404::new().into(),
        }
    }
}
```

`route!(config, get_pet_by_id::GetPetById)` registers the endpoint with actix-web using `Api.path_template()` and
`Api.method()`. Actix-web uses the same `{petId}` syntax as Wirespec for path parameters. For each request, the route:

1. converts the actix-web request to a `RawRequest`,
2. turns it into a typed `Request` with `from_raw_request(&Json, ..)`,
3. calls the `PetStore` handler,
4. converts the `Response` back with `to_raw_response(&Json, ..)` and returns it as an actix-web response.

To serve another endpoint, implement its `Handler` for `PetStore` and add a `route!` line to `configure`.

The generated traits use `async fn`, so their futures are not `Send`. That works with actix-web because it runs each
worker on a single thread. Frameworks that require `Send` handlers, such as axum, need extra work.

### Good to know

- The serialization and transport traits return plain values, not `Result`, so invalid input causes a panic. The
  generated `from_raw_request` also panics when a required parameter is missing.
- Every generated file has `use regex;` at the top, so `regex` is a dependency even though the Petstore has no refined
  types.
